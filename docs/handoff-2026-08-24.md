## 3. Two bugs worth understanding, because both were invisible

### 3a. Tests that inject a service-role client cannot catch RLS bugs

`generated_artifact` grants INSERT to `service_role` only. The ingest path runs as the
signed-in owner, so `record()` was inserting with that caller's client, every insert was
refused by RLS, and the error was swallowed by a `console.error`. Documents were being
created in Google with **no record that ConductFlow made them** — the exact audit answer
the table exists to give.

Production had **zero** `generated_artifact` rows across its entire history. Not "no
successes" — no rows at all.

Every test in `tests/artifacts/for-ingest.test.ts` passed a service-role client, which
bypasses RLS, so none of them could ever have failed. The regression test added
(`"records artifacts even when the caller's client cannot write the table"`) signs a JWT for
a real org member. **When testing anything RLS-sensitive, use that helper, not the
service-role client.**

### 3b. The AI SDK wraps errors, and the first fix was wrong

The gateway rate limit does not arrive as `GatewayRateLimitError`. The AI SDK retries
internally and hands back `AI_RetryError` — no `statusCode` of its own, the real 429 only
reachable through `.lastError` / `.errors[]`. The first version of `isUpstreamRateLimit`
checked only the outermost error and would have shipped doing nothing.

It was caught by probing the live gateway rather than trusting the unit test. `lib/agent/
upstream-limit.ts` now walks `lastError`, `errors[]` and `cause`, bounded against cycles.

### The live hypothesis

`401 invalid_client` means Google does not recognise the client id **the browser sent**.
The picker uses `NEXT_PUBLIC_GOOGLE_CLIENT_ID`; the working server flow uses
`GOOGLE_CLIENT_ID`. They have drifted.

The Console client (`ConductFlow Web`, created 2026-08-12) is:

```
167284676996-0uel39d5r3jbcko7ldehh7kgo9e89k7s.apps.googleusercontent.com
```

`docs/google-enablement-runbook.md` §4.4 requires both variables to be byte-identical.

### The one piece of evidence still needed

**The `client_id` in the URL of the error popup.** The error page URL contains it:

```
…/signin/oauth/error?authError=…&client_id=<THE ANSWER>&aes=…
```

- If it matches the ID above → the env var is fine, look elsewhere; get the DevTools console error.
- If it differs → confirmed drift. Set `NEXT_PUBLIC_GOOGLE_CLIENT_ID` to the ID above and redeploy.

Plausible cause of drift: the OAuth client was created 2026-08-12, the env vars set 12–13
days ago. An earlier client may have been deleted and only `GOOGLE_CLIENT_ID` updated.

### Also unverified

## 10. The picker 401, actually measured — supersedes §5 and §8.1–8.2

§5 guessed that `NEXT_PUBLIC_GOOGLE_CLIENT_ID` had drifted to a client Google no longer
recognises. It had not. Four probes, all run against Google's live endpoints:

| Probe | Result |
| --- | --- |
| Authorize `172736639116-vgafe…` with the prod callback | Reaches the sign-in page — client exists, redirect URI registered |
| Authorize `167284676996-0uel…` with the prod callback | Same — this client exists too |
| Token exchange, `172736639116-vgafe…` + `GOOGLE_CLIENT_SECRET` | **400 `invalid_grant`** — the code was fake, so the *secret is correct* |
| Token exchange, `167284676996-0uel…` + the same secret | **401 `invalid_client`** — wrong secret, different client |
| `NEXT_PUBLIC_GOOGLE_PICKER_API_KEY` against any Google API | Error metadata names `consumer: projects/167284676996` |

Reproduce the third and fourth with a deliberately fake `code`: a wrong secret is rejected
before the code is ever looked at, so the status alone separates them. It is the cheapest
way to ask "which client does this secret belong to" without a browser.

### What that means

**The two halves of the picker are in two different Google Cloud projects.**

- The OAuth client holding every refresh token, every grant, and the working server connect
  flow is `172736639116-vgafe…`, in project **172736639116**.
- The Picker API key is in project **167284676996**, along with the `167284676996-0uel…`
  client that §5 pointed at.

The Picker requires the OAuth token and the developer key to come from the same project. A
`drive.file` grant also binds to the *client id*, which is what makes the browser pick
readable by the server afterwards (`recordPickedTemplates` documents this). So adopting the
`167…` client — §8 step 2 — would have produced files the server could not read, on top of
whatever the picker did next.

The JavaScript origins added during the previous session went onto the `167…` client, which
the browser was never using. That is why fixing them changed nothing.

### The Console work, and it does need a human

In project **172736639116** (the one that owns `172736639116-vgafe…`):

1. OAuth client → **Authorized JavaScript origins**: add `https://conductflow-sooty.vercel.app`
   and `http://localhost:3000`, plus any custom domain. Origins carry no path and no
   trailing slash — that is the difference from an API key's referrers, which need `/*`.
2. Enable **Google Picker API** and **Google Drive API** on that project.
3. Create a **browser API key** there. Restrict it to those two APIs, and to website
   referrers `https://conductflow-sooty.vercel.app/*` and `http://localhost:3000/*`.
4. Set `NEXT_PUBLIC_GOOGLE_PICKER_API_KEY` to the new key and
   `NEXT_PUBLIC_GOOGLE_CLIENT_ID` to `172736639116-vgafe5470dfabv1hupkttvdog47pjh8m.apps.googleusercontent.com`,
   in both Vercel production and `.env.local`. Redeploy — Vercel only picks up an env change
   on a new deployment.

Do **not** change `GOOGLE_CLIENT_ID` or `GOOGLE_CLIENT_SECRET`. Both orgs' refresh tokens
are bound to the `172736639116` client; rotating it revokes both connections.
